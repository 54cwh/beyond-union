# 开工指南（保姆级，照着做）

> 写给不熟悉 git/协作流程的成员。**按顺序一步步做，每步做完检查括号里的结果**。
> 有问题随时问 cwh（E 集成岗），他会统一协调。

---

## 第 1 步：装工具（一次性，约 20 分钟）

检查本机有没有这些，没有就装：

| 工具 | 检查命令 | 没有怎么办 |
|------|---------|-----------|
| Git | `git --version` | 装 Git（Windows 装 Git for Windows）|
| uv | `uv --version` | 官方脚本安装：`curl -LsSf https://astral.sh/uv/install.sh | sh` |
| Python 3.12 | `uv python list` | `uv python install 3.12` |
| Node 18+ | `node --version` | 装 Node LTS（nodejs.org）|

> **结果检查**：三个命令都能显示版本号，就算装好。

---

## 第 1.5 步：装你需要的 AI 技能（一次性，约 10 分钟）

你的 AI 需要装一些"技能"（skill）才能干好活。**每个人装的不一样**，按你的岗位装：

| 你的岗位 | 必须装 | 可选装 |
|---------|--------|--------|
| **所有人**（A/B/C/D/E）| `test-driven-development` · `verification-before-completion` · `webapp-testing` · context7(MCP) | — |
| **A 数据岗**（zzx）| `chinese-documentation` | `drawio` · `systematic-debugging` |
| **B 展示岗**（lcz）| `ui-ux-pro-max` · `frontend-design` · `web-design-guidelines` | `theme-factory` |
| **C 前端**（cjx）| `ui-ux-pro-max` · `frontend-design` · `systematic-debugging` | `web-design-guidelines` |
| **D 前端**（pcx）| `ui-ux-pro-max` · `frontend-design` · `systematic-debugging` | `web-design-guidelines` |
| **E 集成**（cwh）| `requesting-code-review` · `receiving-code-review` · `finishing-a-development-branch` · `subagent-driven-development` · `chinese-commit-conventions` | `chinese-code-review` · `chinese-documentation` · `drawio` |

> **装法**：把 skill 放进你 AI 的技能目录（通常是 `~/.agents/skills/` 或 `~/.claude/skills/`）。**不会装就问 cwh**。
> **提醒**：所有人至少装那 4 个"必须装"，再加自己岗位的必须项。

---

## 第 2 步：拉取代码（一次性）

```bash
git clone git@github.com:54cwh/beyond-union.git
cd beyond-union
```

> **结果检查**：出现 `beyond-union` 文件夹，里面有 `app.py`、`docs/`、`pages/` 等。
> 如果 clone 失败提示认证问题：你的 SSH key 没配置，问 cwh。

---

## 第 3 步：装项目依赖（一次性）

```bash
uv sync                        # 装 Python 依赖（约 1 分钟）
uv run playwright install chromium   # 装测试浏览器内核
npm install                    # 装 Node 依赖（约 30 秒）
```

> **结果检查**：三条命令都不报红。若 uv sync 卡在下载，可能是网络，换网络或问 cwh。

---

## 第 4 步：建你自己的分支（每天开工前确认一次）

**永远不要动 main 分支！** 你在自己的分支上干活。

把下面命令里的 `X` 换成你的岗位代号（a/b/c/d/e），小写：

```bash
git checkout -b feature/X      # 例如 zzx 用: git checkout -b feature/a
```

> **结果检查**：命令行提示符前面显示 `(feature/X)`。
> 以后每次开工：`git checkout feature/X` 切回你的分支，别切到别人分支上。

---

## 第 5 步：读文档（开工第一个任务，约 30 分钟）

**顺序读，别跳**。每个文件都过一遍：

1. `docs/需求.md` —— 产品是啥（"经营决策工作台"，不是数据大屏）
2. `design-system/MASTER.md` —— 颜色/字体/风格（B 维护，你只读）
3. `template.html` —— 页面骨架，**做页面从它复制**
4. `docs/技术栈定案.md` —— 技术铁律（哪些不能做）
5. `docs/分工说明.md` → **"岗位工作区"** —— **你的地盘**（你能碰哪些文件、必写哪些文档）
6. `docs/协作说明.md` → "文件所有权表" —— 哪些文件你不能动

> **结果检查**：能说清"我负责哪些文件、我必写哪些文档、哪些文件我绝对不能动"。

---

## 第 6 步：先写设计文档，再写代码（重要！）

**规则：先文档后代码。** 做你的页面之前，先在你的工作区里写页面设计说明（就是工作区里的"必写文档"）。

例如你是 cjx（C 岗，做 p4）：
1. 先写 `pages/p4.md`（这页有什么模块、怎么交互、用哪些数据）
2. 再开始做 `pages/p4.html`

为什么：**你的 AI 要照着这个文档写代码**，文档越清楚，AI 写得越准，也方便别人理解你在做什么。

---

## 第 7 步：开发 + 本地预览（循环做）

每次改完代码，浏览器里看效果：

```bash
# 启动预览服务器（在项目根目录）
uv run python -m http.server 8000
```

浏览器打开 `http://127.0.0.1:8000/pages/你的页面.html`（如 p4 → `p4.html`）。

**页面从 template.html 复制**：
```bash
# 例如 cjx 做 p4：
cp template.html pages/p4.html
# 然后改 pages/p4.html 里的 title 和内容
```

改过页面样式 class 后，要重新编译 Tailwind：
```bash
bash scripts/build_tailwind.sh
```

> **铁律提醒**：页面里**禁止**自己写筛选/聚合逻辑（那是 zzx 的活）、**禁止**直接 `echarts.init`（用 B 的图表组件）、**禁止**写死本机路径。

---

## 第 8 步：提交前自检（每次提交必做）

```bash
npm test               # 1. JS 单测，必须全绿
uv run pytest          # 2. 契约+页面测试，必须全绿
uv run ruff check .    # 3. Python 规范，必须无报错
```

然后**浏览器里手动点一遍**你的页面：打开、点按钮、看图表，确认没明显问题。

> **结果检查**：三行命令都绿 + 页面手动操作正常，才允许提交。

---

## 第 9 步：提交到你的分支

```bash
git add .                          # 把你的改动暂存
git status                         # 检查：只列了你该改的文件（不该出现别人的文件！）
git commit -m "feat: 描述你做了什么"  # 提交
git push -u origin feature/X        # 推到你自己的远程分支
```

> **提交信息格式**：`feat:`（新功能）/ `fix:`（修 bug）/ `docs:`（改文档）+ 一句中文说明。
> **检查**：push 后去 GitHub 仓库页面，能看到你的 `feature/X` 分支有你的提交。

---

## 常见坑（别踩）

| 坑 | 正确做法 |
|----|---------|
| 在 main 上直接改 | 永远先 `git checkout feature/X` |
| push 到 main | 只 push 你自己的 `feature/X` |
| 改了别人的文件 | 只碰工作区里"你负责"的文件（见第 5 步）|
| 用了绝对路径 `/home/xxx/` | 全部用相对路径（`../assets/` 或 `/pages/`）|
| 页面里自写聚合逻辑 | 用 zzx 的 `filter.js`/`format.js` |
| 直接 `echarts.init` | 用 B 的 `chart-view.js` |
| 写完就交给 AI 提交 | 先自检（第 8 步），再自己确认提交 |
| 不写文档直接写代码 | 先写页面设计文档（第 6 步）|

## 紧急情况

- **测试红了不知道怎么修**：把报错发给 cwh
- **改了公共文件（图表组件/数据文件等）**：通知 cwh，他会协调
- **想加新库/新依赖**：不要自己装！问 cwh
- **跟别人的页面冲突**：停手，找 cwh 协调

---

## 每天的固定流程（总结）

**每天开工第一步：先拉最新代码。** 别人可能改了公共文件（图表组件、数据、模板），你不拉就拿着旧代码开发，最后合并时一堆冲突。

```
1. git checkout feature/X        切到自己的分支
2. git pull origin main          拉最新代码（必做！第一天尤其要拉，拿别人的更新）
3. git pull                      也拉一下自己分支的最新（别人可能动过共享文件）
4. 读一眼 docs/分工说明.md 工作区   记住自己的地盘
5. 开发 → 浏览器预览 → 自检 → 提交 → push
6. 有问题找 cwh
```

> **为什么先拉**：E 集成岗可能改了模板/公共组件，A 数据岗可能更新了数据契约——不拉就开发，等于在旧地基上盖楼。
> **遇到 pull 冲突**：别乱删！停手找 cwh。
