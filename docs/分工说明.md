## 页面结构（对齐《docs/需求.md》V2.0）

**需求原为 12 页，按"MVP 打通预测—优化—交易核心链路"合并为 6 页。功能全部保留，页间有明显区分 + 链路联系。**

### 页面总览
| 页面 | 对应需求页 | 核心功能 | 负责人 |
|------|-----------|---------|--------|
| `p1` 运营工作台 | 01 项目中心 + 02 运营工作台 + 03 数字能源地图 | 项目入口、今日经营结果、明日预测、经营链路图、今日重点、待办、资产地图/区域经营概览 | **B · lcz（展示岗）** |
| `p2` 发电预测中心 | 04 | 预测曲线（实际/预测/置信区间）、风险时间轴、影响因子、模型验证、经营影响 | **D · pcx（前端）** |
| `p3` 风光储优化中心 | 05 | 优化时间轴、四方案 PK、AI 推荐、约束条件 | **D · pcx（前端）** |

### 页间链路（呼应需求"经营链路"）
```
p1 运营工作台（今日/明日总览，入口）

p2 发电预测 → p3 风光储优化 → p4 绿电入市决策（核心）

p6 经营成效（基准/AI/实际三栏对比 + 案例验证 + 数据可信）
```

## 岗位边界（谁决定什么 / 谁不能碰什么）

**核心原则：每个岗位在其领域内拥有决定权；不确定的设计交给对应岗位定，不要擅自替别人决定。**

| 边界 | A（数据岗）| B（展示岗）| C/D（页面）| E（集成）|
|------|-----------|-----------|-----------|---------|
| **拥有的决定权** | 数据契约、ETL、计算层 API、数据质量标准、模拟数据 | chart-view 接口、展示组件库、可信 AI 卡片/溯源组件、图表形态、**前端整体风格（common.css / MASTER.md / tailwind 配置）** | 自己页面的 UI/交互/文案 | 基础设施（common.js/template）、Copilot 壳/问答库、打包、合并门槛 |
| **产出物** | data/*.json、计算层代码、模拟数据、数据质量测试、p6 | chart-view.js、展示组件库、p1、tailwind.css（合并前最终编译）| p4（C）/ p2+p3（D）+ E2E | p5、Copilot 壳、AI 问答库、打包产物、契约测试 |
| **可消费的依赖** | 无（上游源头）| A 的数据契约 | A 的契约+计算层、B 的图表组件 | 所有模块 |
| **不得擅自做的** | 替 B 定图表接口、替 C/D 定页面 UI | 自写计算逻辑、改数据契约 | 自写筛选/聚合/格式化、直接 echarts.init、改共享只读文件 | 替 A/B/C/D 做其领域的设计决策 |

**边界裁断**：
- 数据怎么算、算得对不对 → **A 说了算**
- **前端整体风格、图表怎么画** → **B 说了算**（画什么数据由 A 的契约和页面决定）
- 页面长什么样、交互如何 → **C/D 说了算**（数据与图表来自 A/B，视觉统一听 B 的）
- 公共接口、打包、合不合 → **E 说了算**

**接口交接点**（两处，需双方对齐但单方决定）：
1. **A → B/C/D**：数据契约字段 + 计算层输出形态（A 定）
2. **B → C/D**：chart-view 输入形态（B 定）
- 页面（C/D）是两者的消费者，只按 A/B 的接口取数渲染，不居中调停——接口不一致时由 E 协调裁定

## 关键路径与缓解（务必遵守）

### 1. B 的 chart-view 是全场阻塞点 → 第一优先级冻结接口
- chart-view.js 骨架已就绪且测试绿
- **B 的时间顺序：① 冻结 chart-view 接口 → ② 可信 AI 卡片/溯源组件 → ③ 再做 p1 页面**（Tailwind 合并编译在 Day2 上午）
- 理由：所有页面的图表都依赖 chart-view 和 AI 卡片，接口不定则 C/D/E 全卡；p1 是 B 自己的页可稍后

### 2. A 是唯一上游 → 分两阶段交付
- **阶段一（优先）：模拟数据集 + 契约骨架** —— 字段名 / 类型 / 可筛选字段 + 演示数据（需求里的示例数字可直接用）
- **阶段二：真实数据** —— 真实 CSV 到手后 pandas ETL 替换
- 模拟数据一出，页面立即并行开工，**不用等真实数据**

### 3. 页面依赖 A 和 B → 先用模拟数据开发 UI
- 页面 UI/交互与真实数据无关，先用 A 的模拟数据开发，数据替换只改数据源

### 4. 测试职责边界（防角色冲突）
- **数据质量测试 + 计算层单测由 A 写**（数据岗自查：行数/空值/字段类型/值域 + 计算函数正确性）
- **C/D 只写自己页面的 E2E**，不承担计算层测试
- **test_contract.py 由 E 写**（只管跨模块一致性：文件存在/引用/导航/JSON 合法）
- 分工依据：数据与计算对不对，A 负责自查；公共接口是否一致，E 负责把关

### 5. 打包黑盒前置（防交付前半天才炸）
- **Day1 下午 E 用现有模板打一次"空壳 EXE"**，暴露 Wine/PyInstaller 环境问题，当天处理
- 若 Wine 不可用 → **立即切换 Windows 成员本机打包**（协作说明已有此通道），不要拖到 Day2

### 6. A 晚交付兜底（正式预案）
- A 若 Day1 上午晚交付模拟数据：C/D/B 先**用需求示例数字直接内联渲染 UI**（不依赖数据文件）
- A 数据到位后再切 `data/demo/*.json`——页面结构不变，只改数据源

4. 文档用相对路径引用文件，**禁止绝对路径**
